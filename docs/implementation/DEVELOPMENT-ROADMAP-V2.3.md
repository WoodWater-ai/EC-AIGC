# 一期开发任务拆解与路线图 V2.3

状态：内部执行文档
日期：2026-07-17
产品基线：V2.3
文档职责：前后端任务拆分、里程碑、联调顺序和文档版本管理

本文把三份正式文档拆成可建 GitHub Issue 的开发任务。每个任务应对应一个 Issue。前端执行 `FRONTEND-IMPLEMENTATION-V2.3.md`，后端执行 `../product/BACKEND-TECHNICAL-SPEC-V2.3.md`。分支命名和提交规则遵循各代码仓自身约定。

## 1. 交付节奏

建议分 5 个里程碑：

| 里程碑 | 目标 | 主要产出 |
| --- | --- | --- |
| M0 工程与协作底座 | 让新同事本地跑通、理解边界 | 文档、环境示例、基础目录 |
| M1 账号与资产底座 | 可登录、可上传、可入库 | Auth/RBAC、商品资产、对象存储 |
| M2 任务与生成闭环 | 可创建图片/视频任务并异步生成 | 任务创建、Workflow Engine、Generation Gateway、模特推荐 |
| M3 审核与模板闭环 | 可评分、审核、打回、归档 | 审核工作台、模板中心、AI 助手基础 |
| M4 数据与管理后台 | 可复盘、可配置、可试运行 | 数据看板、系统配置、通知、日志 |

## 2. 所有权矩阵

| 工作项 | Owner | 交付边界 |
| --- | --- | --- |
| 页面、DTO、mock/real adapter、动态表单、状态和结果展示 | Frontend | 不调用 Provider，不修改后端数据语义 |
| 数据表、状态机、快照、事务、队列、Gateway、Skills 编排 | Backend | 提供 `/api/v1` 契约和 OpenAPI |
| 字段命名、错误码、联调样例、验收场景 | Joint | 以三份正式文档为准，变更需同步三份正式文档和受影响的内部执行文档 |
| Provider 能力、成本、健康度和错误映射 | Backend + Algorithm | 前端只消费标准化 Schema 和摘要 |
| 五步流程、审核和付费门禁验收 | Product + Joint | 任一绕过确认链路的实现不得验收 |

## 4. 前后端接口联调顺序

1. 登录和当前用户权限。
2. 商品资产列表和上传。
3. 商品信息识别。
4. 模特资源列表和推荐候选。
5. 创建任务组和子任务，完成商品/来源事实确认和上下文快照。
6. 按子任务生成 Prompt，确认有序参考资产和 Prompt 快照批次。
7. 可用模型通道和能力 Schema。
8. 视频默认 Prompt Profile 初始化，以及目标通道 `compile-prompts-for-channel` 差异和兼容状态。
9. 动态执行参数、有序参考图和组级无付费 Preflight。
10. 成本/耗时/健康度/兜底策略确认和执行快照批次。
11. 原子 Submit 图片任务组进入队列，创建全部初始 generation attempts。
12. Worker 生成图片并校验结果规格。
13. 任务详情读取节点产物、尝试记录和统一 `generation_results`。
14. 评分审核和图片归档。
15. 从图片结果创建视频任务并重复内容确认、通道编译、执行确认流程。
16. 提交视频任务进入队列、保存并校验视频结果。
17. 视频审核、归档和数据看板。

### 4.1 M2 联调交付清单

## 7. 开发注意事项

- 前端和后端分别在各自代码仓开发，不把项目资料父目录作为代码仓。
- 不提交 `public/uploads/`、`public/generated/`、`tmp/`、`output/` 中的运行时文件。
- 不提交真实 API Key、token、密码。
- 不在普通 PR 中混入数据库迁移、CI/CD、部署配置，除非任务明确要求并已确认。
- 现有 demo 中飞书字段、提示词和模型调用逻辑可以复用为业务参考，但正式产品以数据库和模型通道为主。

## 8. 一期完成定义

一期可试运行需要满足：

- 20+ 内部员工可账号登录。
- 管理员可创建账号、分配角色。
- 运营可上传素材、创建生成任务。
- 系统可异步调用模型通道生成结果。
- 设计/美工可评分并打标签。
- 审核人可上架审核、打回或归档。
- 素材资产可按商品沉淀。
- 管理者可查看任务、质量、成本和资产指标。
- 模型通道和模板可由管理员/设计维护。
- 失败、重试、成本、耗时、操作日志可追踪。
- 任一付费生成均可追溯到 Prompt 确认、Preflight、执行确认和 Submit 幂等键。
- 任务组任一子任务 Preflight 失败时整组不能提交，且不存在部分入队。
- 视频阶段 3 可按默认通道 Profile 初始化 Prompt，阶段 4 切换通道后可展示差异并刷新动态参数。
- `syntax_only` 保留内容确认，`content_revision_required` 返回阶段 3；Profile 缺失或不兼容不能进入 Preflight。
- 视频镜头按 5s/8s/15-16s 动态生成，Vidu 专有语法只存在于 Vidu Profile 编译结果。

### 9.2 版本升级

所有五份文档共享一个产品基线版本，不再独立维护 V1.0、V1.3 等版本号。

需要升级产品基线的变化：

- 产品范围、业务流程、页面行为或验收标准变化。
- 状态、任务 Profile、快照、结果来源或付费门禁语义变化。
- API 路径、请求响应字段、错误码或调用顺序发生不兼容变化。
- 数据对象、事务边界、Skills 或 Provider 接入边界发生实质变化。

升级方式：

1. PRD 从 V2.3 升至 V2.4。
2. 其余四份文件同步改名和更新 `产品基线`，即使某份内容没有功能变化也必须声明“本基线无功能变更”。
3. 同一个 Pull Request 内完成五份文档引用更新。
4. 仓库只保留当前版本文件；历史内容由 Git 记录，不创建“副本”“最终版”“最新版”等文件。
5. 对外发送时只打包当前三份正式文档。

不需要升级产品基线的变化：

- 错别字、排版和不改变语义的示例修正。
- 实现进度、Issue 编号、负责人或排期变化。
- OpenAPI 自动生成内容与既定 API Contract 的等价同步。

以上修改直接提交到当前文件，由 Git commit 记录修订历史。

### 9.3 变更流程

1. 产品先更新 PRD 并标明行为变化。
2. 前后端共同确认 API Contract 是否受影响。
3. 后端确认数据模型、事务和 Provider 是否受影响。
4. 前端、后端实施文档同步任务拆解。
5. 完成状态枚举、Profile、JSON 示例、关键场景和引用路径检查后，基线生效。

任何付费链路变更都必须重新验证：

```text
确认 Prompt -> 选择通道和参数 -> Preflight -> 用户确认执行 -> Submit
```
